# 設計

## 全体方針

Step 3 は「時間」と「隠し情報」という2つの厄介な要素を、**型と関数シグネチャの設計だけで無害化する**ことを主眼に置く。

| 厄介な要素     | 設計上の解決                                                                          |
| -------------- | ------------------------------------------------------------------------------------- |
| 宣言の制限時間 | エンジンは時計を持たず `TICK(deltaMs)` を受け取るだけ。実時間は Step 4 の UI 層が供給する |
| 他家の手札     | AI に `GameState` を渡さず、公開情報だけを含む `AiView` を渡す。カンニングを型で不能にする |
| 割り込みの競合 | `claimWindow` を明示フェーズ化し、優先度解決を独立した純関数として単体テストする         |
| 連続宣言の暴走 | 補充で山札が必ず減ることに加え、`maxChainDeclare` のガードと山札単調減少の assert を置く |

## 持ち越し課題の決着

Step 1 から持ち越していた **`rules` の受け渡し方**をここで確定させる。

### 決定: `reduce(state, action, rules)` — `GameState` に埋め込まない

| 案                              | 採用 | 理由                                                                                                |
| ------------------------------- | ---- | --------------------------------------------------------------------------------------------------- |
| A. `reduce(state, action, rules)` | ✅   | 既存エンジン関数（`findYaku` / `scoreYaku` / `setupGame`）がすべて `rules` を引数で受け取る形と一貫する |
| B. `GameState.rules` に埋め込む   | ❌   | 状態スナップショットが肥大化し、テストの差分比較・React の再描画コストが無駄に増える                   |

`GameState` は**純粋なデータのスナップショット**であり続ける。`rules` は1局を通じて不変な設定であって局の状態ではない、という区別を型に反映させる。

**案 B が防ごうとしていたリスク**（対局中に別の `rules` を渡されて壊れる）は、以下で代替する:

- `reduce` は毎回 `rules` から期待手札枚数などを導出して不変条件を検査するため、途中で異なる `rules` を渡すと**沈黙して壊れるのではなく検査で落ちる**
- Step 4 の `useGameLoop` は `rules` を1度だけ受け取り、フック内で保持する（呼び出し側が毎回渡す形にしない）

## 状態機械

### フェーズ遷移図

```
createGame
    │
    ▼
  draw ──── DRAW ────► selfDeclare ────────┐
    ▲            declarer = turn   │   ▲   │ チェーン脱出（SKIP_DECLARE / チェーン上限）
    │            chainCount = 0    │   │   │
    │                              │   │   ├─ declarer === turn（ツモチェーン）
    │                     DECLARE ─┘   │   │       ▼
    │                     消費→補充 ───┘   │     discard ── DISCARD ──► claimWindow
    │                     chainCount++     │                                │
    │                                      │              CLAIM / PASS / TICK│
    │                                      │                                ▼
    │                                      │                          resolveClaim
    │                                      │                          （過渡・外部から見えない）
    │                                      │                            │        │
    │                                      └─ ロン成立 ─────────────────┘        │ 誰も割り込まない
    │                                         settleRon → 消費→補充                │
    │                                         declarer = ロンした人                │
    │                                         turn は据え置き                      │
    │                                                                             │
    └─── declarer !== turn（ロンチェーン脱出）───────────────────────────────────┘
              turn を1つ進めて draw へ

  いつでも: 山札が尽きる / 誰かの点数が0以下 → gameOver
```

図の右下2本の矢印が示すとおり、**`draw` へ戻る経路は2つある**。ロンチェーンを抜けたときは `discard` を経由しない（`turn` のプレイヤーは既に捨て終わっているため）。`Action` の `DISCARD` は対象プレイヤーを持たず常に `state.turn` を対象とするので、ここを一本化すると「既に捨てたプレイヤーにもう一度捨てさせる」バグになる。

### `resolveClaim` の扱い（過渡フェーズ）

`resolveClaim` は**外部からアクションを受け付けない過渡フェーズ**である。`claimWindow` を閉じるアクション（最後の `CLAIM` / `PASS`、または時間切れの `TICK`）の内部で解決まで一気に進み、`reduce` が `resolveClaim` のまま返ることはない。

型に残しておくのは、遷移の途中経過を `GameEvent` の並び順として説明するときの語彙として有用なため。**`reduce` の戻り値の `phase` が `resolveClaim` になっていたらそれ自体がバグ**であり、テストで固定する。

### `declarer` フィールドの追加

`GameState` に **`declarer: PlayerId`** を追加する（`types.ts` を拡張）。

`selfDeclare` フェーズで宣言権を持つプレイヤーを表す。これがないと「ロンした人が補充後に連続宣言する」状況を表現できない（`turn` は捨て札を出した人のままであり、宣言者とは別人になる）。

チェーン終了時の分岐は `declarer` と `turn` の一致で判定できる:

| 状況         | `declarer === turn` | チェーン終了後の遷移             |
| ------------ | ------------------- | -------------------------------- |
| ツモチェーン | ✅ 真               | `discard`（引いた1枚をまだ持つ） |
| ロンチェーン | ❌ 偽               | 次のプレイヤーの `draw`          |

**ロンチェーンで両者が一致しない根拠**は、`settleRon` が自己ロンを拒否することではなく（それが効くのは初回のロン成立時だけで、2回目以降のチェーン内宣言はツモとして精算される）、**チェーン中は `turn` を一切再代入しないという設計判断そのもの**である。ロン成立時に `declarer` にはロンしたプレイヤー（≠ `lastDiscardBy` = `turn`）が入り、チェーンを抜けるまでどちらも変わらない。

### `declarer` のライフサイクル

| タイミング         | `declarer`               | `chainCount` |
| ------------------ | ------------------------ | ------------ |
| `createGame`       | `turn`（= 0）            | 0            |
| `DRAW`             | **`turn` に設定し直す**  | **0 にリセット** |
| `DECLARE` 成立     | 変えない                 | +1           |
| ロン成立           | ロンしたプレイヤーに設定 | 1 にリセット |
| チェーン脱出       | 変えない（次の `DRAW` で上書きされる） | 変えない |

`DRAW` での `declarer = turn` の設定は**省略しやすく、かつ省略すると後述の手札枚数検査が静かに誤動作する**（前局面のロンチェーンの `declarer` が残る）ため、`DRAW` ハンドラのタスクとして明示する。

### 手札枚数の不変条件

**手番プレイヤーは、引いてから捨てるまでの間だけ1枚多く持つ。**

素朴に「`playerId === turn` かつ `phase ∈ {selfDeclare, discard}` なら +1」と定義すると**誤りになる**。ロンチェーン中は `phase` が `selfDeclare` のまま `turn` が捨て終わったプレイヤーを指し続けるため、既に7枚に戻っている `turn` のプレイヤーに8枚を期待してしまう。

正しくは「+1 枚を持つのはツモチェーン中の手番プレイヤーだけ」であり、`declarer === turn` をゲート条件に加える:

```
expectedHandSize(state, playerId, rules) =
  rules.handSize
  + (playerId === state.turn && state.declarer === state.turn
     && phase ∈ {selfDeclare, discard} ? 1 : 0)
```

ロンチェーン中（`declarer !== turn`）は**全員が `handSize` 枚**になる。ロンしたプレイヤーも補充によって `handSize` 枚に戻っているためである。

### 補充枚数の規則

**補充枚数 = 役として消費したカードのうち、自分の手札から出た枚数。**

| 和了種別 | 手札 | 消費 N 枚の内訳         | 補充  | 結果      |
| -------- | ---- | ----------------------- | ----- | --------- |
| ツモ     | 8枚  | すべて手札から          | N 枚  | 8枚（維持） |
| ロン     | 7枚  | 1枚は捨て札、N-1枚が手札 | N-1枚 | 7枚（維持） |

この1つの規則で両方が説明でき、上の `expectedHandSize` と自動的に整合する。

### 補充中に山札が尽きた場合

**精算は常に確定させ、補充は取れるだけ取る。** 和了そのものを取り消す（ロールバックする）方式は採らない。

1. `settleTsumo` / `settleRon` を必ず実行する（点数移動は確定）
2. 消費カードを手札から除く
3. `min(必要枚数, 山札残り)` だけ補充する
4. 補充が足りなければ、そのステップの最後に `gameOver(wallEmpty)` へ遷移する

ロールバック方式を採らないのは、和了は既に公開された事実であり「山札が足りなかったので無かったことにする」という挙動がゲームとして不自然なうえ、部分的に適用された状態を巻き戻す処理がカード保存則を壊す最大の温床になるためである。

この結果、`gameOver` に到達した局面に限り手札が `handSize` 未満になりうる。不変条件の検査は `phase !== 'gameOver'` を前提とする。

### 連続宣言の上限ガード

`maxChainDeclare` のガードは**アクションを拒否する形では実装しない**。「役が成立していれば必ず宣言する」CPU AI に対して `DECLARE` を例外で弾くと、自動対局が上限到達のたびに例外で止まってしまう。

代わりに**遷移時に適用する**: `DECLARE` を1回処理した直後に `chainCount >= maxChainDeclare` なら、`selfDeclare` へ戻らずそのままチェーンを脱出する。

```
DECLARE 処理 → chainCount++ → chainCount >= maxChainDeclare ?
                                 ├ Yes → チェーン脱出（discard または次の draw）
                                 └ No  → selfDeclare を継続
```

これにより **`reduce` の戻り値が「`selfDeclare` かつ `chainCount >= maxChainDeclare`」になることは決してない**。AI は上限を知る必要がなくなり、`AiView` に `chainCount` を含めずに済む（AI は公開情報だけで判断するという設計が保たれる）。

上限に到達させるテストは、`maxChainDeclare` を小さくした `rules` を注入して行う。

### 割り込み優先度の解決

独立した純関数として実装し、状態機械から切り離して単体テストする:

```ts
resolveClaimWinner(
  claims: Readonly<Record<PlayerId, ClaimDecision>>,
  discarder: PlayerId,
  playerCount: number,
): { playerId: PlayerId; candidate: YakuCandidate } | null
```

1. `pass` と未決定を除外する
2. `candidate.score` が最大のものを選ぶ
3. 同点なら `(playerId - discarder + playerCount) % playerCount` が小さい方（捨てた人から反時計回りに近い方）を選ぶ

勝者以外は何も得ず、支払いも発生しない（頭ハネ）。

### 終了判定

| 理由        | 判定タイミング                                             |
| ----------- | ---------------------------------------------------------- |
| `wallEmpty` | `DRAW` 時に山札が空 / 補充に必要な枚数を山札が供給できない  |
| `bankrupt`  | 精算のたびに全プレイヤーの点数を検査し、0以下の者がいれば終了 |

0クランプにより点数は負にならないため、`bankrupt` は実質「ちょうど0になった」場合を指す。

**和了1回の中での処理順序は `精算 → 消費 → 補充 → 終了判定` に固定する。** 破産と山切れが同時に成立した場合は `bankrupt` を優先する（点数のやり取りがゲームの主目的であり、そちらを終了理由として報告する方が情報量が多いため）。終了判定を最後に置くことで、破産で終わる局でも補充まで完了した一貫した状態が残り、カード保存則の検査が終了局面でも成立する。

順位は点数降順、同点はプレイヤー ID 昇順で決定する（決定性のため）。

### 不正な候補への防御

`DECLARE` / `CLAIM` が運ぶ `YakuCandidate` は**呼び出し側が作ったデータであり、信頼できない**。UI のバグや将来のネットワーク対戦を考えると、点数を偽装した候補をそのまま精算に流すわけにはいかない。

そこで `reduce` は受け取った候補を捨て、**現在の手札から `findYaku` を再実行して同一のものを探し直す**。照合は「消費カードの uid 集合 + 役種 + 同色可否」で行い、実際に採用するのは**再計算された候補**とする。点数は常にエンジンが計算した値になる。

これは「入力を検証する」のではなく「**入力を再計算で置き換える**」設計であり、点数フィールドの偽装が原理的に効かなくなる。

再計算に使う呼び出しは宣言の種別で異なる:

| アクション | 再計算に使う呼び出し                                | 意味                                       |
| ---------- | --------------------------------------------------- | ------------------------------------------ |
| `DECLARE`  | `findYaku(hand, ctx)`                                | 手の内だけで成立する役（ツモ）              |
| `CLAIM`    | `findYaku([...hand, discard], ctx, discard)`         | その捨て札がなければ成立しない役（ロン）    |

**`CLAIM` の再検証は割り込み解決時ではなく、`CLAIM` アクションを受理する瞬間に行う。** `resolveClaimWinner` は手札を受け取らない純関数（優先度の比較だけを担う）であるため、その時点では再計算できない。`state.claims` に格納するのは**再計算された候補**であり、不正な `CLAIM` はその場で例外になる。

`DECLARE` は `state.declarer` 以外のプレイヤーが送っても例外とする（`CLAIM` を手番プレイヤーが送れないことの対称）。

## CPU AI

### 隠し情報の遮断

AI 関数は `GameState` を受け取らない。公開情報だけを持つ **`AiView`** を受け取る:

```ts
interface AiView {
  readonly selfId: PlayerId
  readonly hand: readonly Card[]          // 自分の手札のみ
  readonly ctx: YakuContext               // 登場グループ・ボーナス・ルール
  readonly discardsByPlayer: readonly (readonly Card[])[]  // 河（全員に見えている）
  readonly wallCount: number              // 残り枚数だけ。中身は見えない
  readonly scores: readonly number[]      // 点数（全員に見えている）
}
```

`toAiView(state, playerId, rules)` が `GameState` に触れる唯一の場所となる。**他家の手札を渡す経路が型として存在しない**ため、カンニングは実装ミスではなく型エラーになる。

山札は `wallCount`（枚数）だけを渡し、中身の配列は渡さない。

### ターゲット評価

各ターゲット（登場メンバーごとの3カード / 登場グループごとのN人組）について、手札から `need`（あと何種類のカードが必要か）と、成立したときの点数を求める。

- 同色成立の可能性も別ターゲットとして数え、期待点の高さを評価に反映する
- 価値は `score / (need + 1) ^ patience` で割り引く。`need` が大きいほど遠く、実現しにくいため

Step 2 の `computeWaits` は**1手先専用**であり、`need >= 2` の評価には使えない（Step 2 の申し送り事項）。転用せず、ここで独自に数え上げる。

### 捨て札の選択

各手札カードについて「それを捨てたときの残りターゲット価値の合計」を求め、**最も損失が小さいカード**を捨てる。同点は uid 昇順で決定的に決める。

`safety` パラメータが0より大きい場合、終盤に限って「他家の河に出ていないメンバーのカード」を減点する。公開情報である河だけを根拠にする。

終盤の閾値は `wallCount < deckSize × 0.2`（既定値では残り20枚）とする。実装時に恣意的な定数を埋め込まず、割合として `rules` から導出する。

### 宣言の判断

v1 は攻略定石どおり **「役が揃ったら即宣言」**。`findYaku` の全候補から `bestYaku` で最良を選んで返す。

- `decideDeclare`（ツモ）: `findYaku(hand, ctx)` — 手の内だけで成立する役を探す
- `decideClaim`（ロン）: `findYaku([...hand, discard], ctx, discard)` — その捨て札を消費し、かつ捨て札なしでは成立しない役だけが返る

`reduce` 側が同じ呼び出しで再計算するため、AI が返した候補は必ず検証を通る。

Step 2 の申し送りどおり、`bestYaku` に AI の戦術評価を継ぎ足すことはしない。`bestYaku` は「エンジンが同点候補を決定的に1つ選ぶ」ためのタイブレークであり、AI 側の評価とは責務が異なる。

### 難易度パラメータ

```ts
interface AiConfig {
  readonly patience: number  // need の遠さをどれだけ割り引くか（大きいほど近い役を優先）
  readonly safety: number    // 終盤の放銃回避の強さ。0 で無効
}
```

`AI_PRESETS` として `easy` / `normal` / `hard` を用意する。AI は乱数を使わないため、同じ `AiView` と `AiConfig` に対して常に同じ判断を返す。

## 自動対局

```ts
playGameToEnd(options: {
  roster, rules, seed, ai?, maxSteps?, onStep?
}): AutoplayResult
```

全員 CPU として、フェーズごとに AI の判断をアクションへ変換して `reduce` を回す。

- `onStep` フックで各ステップの状態を外から検査できる（テストが不変条件を全ステップで確認するため）
- `maxSteps` を超えたら例外を投げる。無限ループは**握りつぶさずバグとして表面化させる**
- `claimWindow` は CPU が即決するため `TICK` を使わない。`TICK` 経路は `game.test.ts` で別途テストする

返す統計:

```ts
interface AutoplayResult {
  readonly seed: number
  readonly reason: GameOverReason
  readonly finalScores: readonly number[]
  readonly ranking: readonly PlayerId[]
  readonly discardCount: number   // 打牌数
  readonly declareCount: number   // 宣言回数（ツモ + ロン）
  readonly ronCount: number
  readonly steps: number
}
```

### 統計回帰テストの方針

計画書は実機の実測値（山切れ終了率 69.7% / 平均35打牌）を参照レンジとして挙げている。ただし本実装の AI とルール推定値は実機と完全一致しないため、**まず100局を実測し、得られた値を基準にテストを書く**。

- 実測値が計画のレンジ内に収まればそのまま採用する
- 外れた場合は、値を都合よく書き換えるのではなく、**実測値を基準にした回帰テスト**（変化の検知が目的）とし、実機との乖離を design.md とユーザー報告に明記する

回帰テストの目的は「実機の再現度の証明」ではなく「**AI やルールを変更したときに分布が壊れたことを検知する**」ことである。この違いをテストのコメントに明記する。

### 実測結果（シード 0〜99 / 既定ルール・既定 AI）

| 指標           | 本実装の実測 | 計画書が挙げる実機の実測 | 判定       |
| -------------- | ------------ | ------------------------ | ---------- |
| 山切れ終了率   | **40%**      | 69.7%（レンジ 60〜80%）  | ❌ 下回る  |
| 平均打牌数     | **21.7**     | 約35（レンジ 30〜45）    | ❌ 下回る  |
| 平均宣言回数   | 13.6         | （記録なし）             | —          |
| 平均ロン回数   | 6.5          | （記録なし）             | —          |
| 4人の点数合計  | 常に 4000    | —                        | ✅ 保存則成立 |

計画書のレンジを両方とも下回った。**値を都合よく書き換えず、実測値を基準にした回帰テストとして記録する。**

#### 乖離の原因分析

`startingScore` を振って100局ずつ回すと、山切れ終了率はこの値に極端に敏感だった:

| `startingScore` | 山切れ終了率 | 平均打牌数 |
| --------------- | ------------ | ---------- |
| 1000（既定・推定値） | 40.0%   | 22.4       |
| 1500            | 82.0%        | 27.1       |
| 2000            | 98.5%        | 28.0       |
| 2500 以上       | 100%         | 28.1（飽和） |

つまり本実装で終局を決めているのは主に**破産**であり（60%）、実機の 30.4% とは逆転している。実機の 69.7% を再現する `startingScore` は 1300〜1400 付近と推定される。

**それでも `startingScore` を 1400 に変更しない。** 破産をすべて取り除いても平均打牌数は 28.1 で飽和し、実機の約35には届かないためである。これは初期点とは独立した差、すなわち **CPU の宣言方針の違い**を示している。本実装の AI は「役が揃えば即宣言」（v1 の定石）のため1局あたり 13.6 回宣言し、そのたびに3〜5枚を補充して山札を余分に消費する。実機の打牌数がより多いのは、実際のプレイヤーが安手を見送っている（＝「ダマポカジャン」的な打ち回しをしている）ことを示唆する。

未確定の `startingScore` を1つの統計から逆算すると、本当は AI の挙動に由来する誤差を初期点に押し付けることになる。`startingScore = 1000` は推定値のまま `TODO(要実機確認)` として残し、上記の感度分析を判断材料として記録するに留める。

この乖離は Step 3 の完了を妨げるものではない。本ステップの目的は「ゲームとして成立していること」の証明であり、点数保存則・カード保存則・手札枚数不変が100局の全ステップで成立していることで達成されている。

当初は `game.ts` / `ai.ts` / `autoplay.ts` の3ファイルを想定していたが、`game.ts` が 641 行に達したため
（「400 行を超えたら切り出す」という本ドキュメントの取り決めに従い）責務ごとに分割した。最終的な構成:

## テスト戦略

Step 2 の振り返りで得た「**構造的整合性のテストだけでは偽陰性を検出できない**」という教訓を、本ステップでは以下の形で適用する。

| 手法                 | 何を守るか                                                                     |
| -------------------- | -------------------------------------------------------------------------------- |
| 不変条件の全ステップ検査 | 点数保存則・カード保存則・手札枚数を、100局 × 全ステップで検査する               |
| 具体的な局面の再現   | 割り込み優先度・連続宣言・両終了理由は、手札を固定した決定的なケースで検証する     |
| 例外の検証           | 不正アクション・偽装候補が**確かに例外を投げる**ことを検証する（黙って通らない）  |
| 統計回帰             | 100局の分布が想定範囲に収まること。AI 変更時の破綻を検知する                      |

**カード保存則**を特に重視する。山札・手札・河・消費済みの合計と uid の一意性を検査することで、「補充で山札のカードが複製された」「消費したカードが河にも残っている」といったカードの湧き出し・消失を検出できる。手札枚数だけを見るテストではこれらを見逃す。

## レビューを受けて追加した防御

コードレビューで挙がった指摘のうち、設計判断として記録しておくべきもの:

- **`reduce` の `switch` に `default` を置き、`never` による網羅性検査を入れた**。`switch` の後に
  `return` があるため、`default` がないと未知の `type` が**どの分岐にも入らず素通りして
  「状態が変わらない」形で黙って成功**してしまう。`IllegalActionError` の存在意義そのものに
  反する穴だった。`Action` に種別を足して `case` を書き忘れた場合もコンパイルエラーで気づける
- **`GameState.phase` を `ObservablePhase`（過渡フェーズ `resolveClaim` を除いた型）にした**。
  「`reduce` は `resolveClaim` のまま返らない」という保証がテストにしかなかったため、型でも表明する。
  併せて `fromDraft` に実行時チェックを置き、Step 4 の UI が `phase` で網羅的に分岐したときに
  到達しないケースを書かされずに済むようにした
- **`Draft` を `GameState` からのマップ型で導出した**。手書きの独立した型にしていると、
  `GameState` にフィールドを足したのに `toDraft` を更新し忘れても**コンパイルが通ってしまう**。
  導出型にすることで取りこぼしが型エラーになる
- **`rules.playerCount` と対局人数の整合を `reduce` の入口で検査するようにした**。
  「途中で `rules` を差し替えたら検査で落ちる」と本ドキュメントに書いておきながら、
  実際にはどこにも検査がなかった。ドキュメントの主張に実装を追いつかせた
- **`lastDiscardBy as PlayerId` のキャストを `requireDiscarder()` に置き換えた**。
  README の設計方針「正しさを『たまたま成り立っている条件』に依存させない」に反しており、
  前提が崩れたときに `undefined` 添字という分かりにくい壊れ方をするところだった
- **`claims` を `Partial<Record<...>>` にした**。実態は「捨てた人以外だけが埋まる部分マップ」であり、
  全キーが埋まる `Record` は嘘をついていた。「割り込みの対象外」と「まだ未表明」を
  型の上でも区別できるようになり、エラーメッセージも正確になった
- **`defaultMaxSteps` にプレイヤー数を反映した**。`deckSize × 20` の固定係数は4人であることに
  暗黙に依存しており、Step 6 で人数を増やすと**正常に終局する対局を「無限ループ」と誤検知**する
  ところだった

## Step 4 へ申し送る設計課題

- `reduce` は `resolveClaim` のまま返らないため、UI が「ロン発生」を検知する手段は**返却された `GameEvent[]` の並び**である。フェーズをポーリングして演出を組まないこと
- `claimWindow` の `TICK` は UI 層が `requestAnimationFrame` などで供給する。エンジンは経過時間を自分で測らないため、タブが非アクティブになったときの挙動は UI 層の責任になる
- CPU の思考時間（演出上のディレイ）はエンジンに存在しない。`useGameLoop` が `setTimeout` で間を作る
### 決定: エンジンと React の接続は「UI 層のラッパー状態 + `useReducer`」

`reduce` は React の `useReducer` の契約（`(state, action) => state`）とそのままでは噛み合わない。
引数が3つあり、戻り値が `{ state, events }` だからである。素直に載せると UI がアニメーションに
使う `events` が捨てられてしまう。

検討した3案のうち、**UI 層にラッパー状態を置く案**を採用する（ユーザー決定）。

| 案                                          | 判断                                                              |
| ------------------------------------------- | ----------------------------------------------------------------- |
| `GameState` に `lastEvents` を持たせる      | ❌ 純粋なドメインスナップショットという前提が崩れ、等価比較テストとセーブ/リプレイに演出情報が混ざる |
| `useState` + 自前ディスパッチ               | ❌ `TICK` のたびに最新状態を読む必要があり、更新関数内で副作用を起こすと StrictMode で演出が2回走る |
| **UI 層のラッパー状態 + `useReducer`**      | ✅ **採用**                                                       |

**エンジンは一切変更しない。** `reduce` のシグネチャは現状のままで、以下は全て
`src/ui/hooks/useGameLoop.ts`（UI 層）に置く。

```ts
/** UI 層だけが持つ状態。エンジンの GameState は純粋なまま保つ。 */
interface LoopState {
  readonly game: GameState
  /** 演出待ちのイベントキュー。UI がアニメーションを再生し終えたら削る。 */
  readonly pending: readonly GameEvent[]
}

/** ドメインのアクションと、UI 専用のアクションを別 union に保つ。 */
type LoopAction = { type: 'ENGINE'; action: Action } | { type: 'EVENTS_CONSUMED'; count: number }

/** rules を束縛したリデューサを返す。useMemo で1回だけ作る。 */
function createLoopReducer(rules: RulesConfig): (state: LoopState, action: LoopAction) => LoopState
```

採用理由の中心は **`TICK` との相性**である。宣言受付のタイマーは UI から `TICK` を送り続けて
駆動するが、`useReducer` の `dispatch` は現在の状態を読まずに呼べるため、状態を依存に持たない
タイマー効果をそのまま書ける。`useState` 方式では最新状態を参照するために `stateRef` が必要になり、
状態と ref の二重管理になる。CPU の思考ディレイ（`setTimeout`）も同じ理由で `useReducer` の方が素直。

実装時の注意:

- `createLoopReducer` が返すリデューサは**純粋関数のまま保つ**。イベントの消費（アニメーション再生）は
  リデューサの中ではなく、`pending` を見る `useEffect` 側で行う
- `ENGINE` アクションで `IllegalActionError` が飛びうる。UI は不正なアクションを出さない前提だが、
  握りつぶさずに表面化させること（`reduce` 側の設計意図がここで無になる）
- `events` はキューに積むので、演出が追いつかないうちに次のアクションが来ても取りこぼさない
- **公開関数の呼び出し規約が揃っていない**。`createGame(roster, rules, seed, options)` は位置引数、
  `playGameToEnd(options)` は全部オプションオブジェクト。UI から複数のエンジン関数を呼ぶ前に
  どちらかに寄せるか判断する
- `SKIP_DECLARE` / `DISCARD` / `TICK` は `playerId` を持たず、常に `state.declarer` / `state.turn` を
  対象とする。ローカル対局では曖昧さがないが、将来ネットワーク対戦にするなら
  「誰がそのアクションを送ってよいか」の検証はエンジンではなくセッション層の責務になる
