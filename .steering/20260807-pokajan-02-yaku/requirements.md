# 要求内容

## 概要

ポカジャン再現ウェブゲームの **Step 2（役判定・点数・支払い）** として、手札から成立している役を列挙する `yaku.ts`、役の点数を算出する `score.ts`、和了時の点数移動を行う `settle.ts` を純粋 TypeScript で実装する。

UI は実装せず、Vitest によるテストのみで正しさを検証する。Step 1 の型（`Card` / `YakuContext` / `YakuCandidate` / `RulesConfig`）と `setupGame` の出力だけを前提とする。

## 背景

ポカジャンの役は「同一メンバー3枚」と「グループ全員1枚ずつ」の2系統しかないが、以下の点で判定が単純ではない。

- **同色の判定が役の点数を大きく変える**（3カードは 120 → 840 と 7 倍）。どの色の組み合わせで和了するかを選ぶ余地がある
- **ボーナスメンバーが役に含まれると1枚につき +90 点**。3カードでボーナスメンバーを揃えると +270 点になる
- **ロン（他家の捨て札での和了）は「その1枚がなければ成立しない」ことが条件**。既に手の内で成立している役でロンを主張できてはいけない
- **リーチ表示（あと1枚で揃うカードの黄色枠）** のために、待ちカードの集合を求める必要がある

この役判定の正しさがゲーム全体の正しさを決めるため、Step 3（対局状態機械）に進む前にテストで固めきる。

## 実装対象の機能

### 1. 役判定（`src/engine/yaku.ts`）

- 手札から成立している役候補をすべて列挙する
- 同色成立を検出し、通常版と同色版の両方を候補として返す
- ロン判定用に「指定した1枚がなければ成立しない候補」だけに絞り込める
- 候補が複数あるとき最良のものを選ぶ
- リーチ表示用に、あと1枚で役が完成するカードの種類と、それに寄与している手札カードを求める

### 2. 点数計算（`src/engine/score.ts`）

- 役種・同色可否・ボーナス枚数から点数を算出する
- 点数表は `RulesConfig.scores` から取得し、ハードコードしない

### 3. 支払い処理（`src/engine/settle.ts`）

- ツモ和了: 自分以外の全員から等分で徴収する
- ロン和了: 放銃者が全額支払う
- 支払い後に点数が負にならないようクランプする
- クランプが発生しても**場全体の点数の総和が変わらない**

## 受け入れ条件

### 役判定

- [x] 同一メンバー3枚で `triple` 役が成立する
- [x] 3人 / 4人 / 5人グループの全員を1枚ずつ揃えると `group3` / `group4` / `group5` が成立する
- [x] 今局に登場していないグループでは役が成立しない
- [x] 役の構成カードが全て同色のとき `sameColor: true` の候補が返る
- [x] 同色が成立しうる色が複数あるとき、その色数だけ候補が返る
- [x] 役が成立していない手札では空配列が返る
- [x] 候補の `cards` の長さが役種と一致する（`triple` は3枚、`groupN` はN枚）
- [x] 同一のカード集合を消費する候補が重複して返らない
- [x] `required` を指定すると、その1枚を含み、かつ**その1枚がなければ同じ役が成立しない**候補だけが返る
- [x] 手の内で既に成立している役は `required` 指定時に返らない（ロンを主張できない）
- [x] **混色で既に成立している役でも、`required` によって同色版に格上げされる場合はロンとして認められる**（誤ロン防止ロジックのちょうど裏返しにあたる意図的な仕様。カード集合の比較だけで誤ロンを判定すると、この正当なロンまで弾いてしまう）
- [x] グループ人数が 3〜5 の範囲外なら例外を投げる（誤った役種を黙って返さないためのフェイルセーフ）
- [x] `sameColor` が実際に消費するカードの色から判定される（点数の大小関係や重複除去の挿入順に依存しない）
- [x] グループ定義にメンバー重複があっても、同じカードを二重に数えて役が誤成立しない
- [x] `RulesConfig` のグループ人数設定が役判定の対応範囲（3〜5人）を外れていたら、対局開始前に `validateRoster` が弾く
- [x] `bestYaku` が点数最大の候補を返す。同点なら残り手札の価値が高い方を選ぶ
- [x] `computeWaits` が、あと1枚で役が完成するカードの種類を過不足なく返す
- [x] `computeWaits` が、待ちに寄与している手札カードの uid を返す（リーチ表示のハイライト用）
- [x] 役が既に成立している手札に対しても `computeWaits` が破綻しない

### 点数計算

- [x] 通常の点数が `RulesConfig.scores[kind].base` と一致する
- [x] 同色の点数が `RulesConfig.scores[kind].sameColor` と一致する
- [x] ボーナスメンバー1枚につき `bonusPerCard` が加算される
- [x] 3カードでボーナスメンバーを揃えた場合、ボーナスが3枚分加算される
- [x] グループ役では、グループ内のボーナスメンバー数だけ加算される
- [x] 点数がルール設定から取得され、定数がハードコードされていない

### 支払い処理

- [x] ツモ時、自分以外の全員が等分を支払う
- [x] ロン時、放銃者だけが全額を支払う
- [x] 和了者の点数が、実際に徴収できた合計だけ増える
- [x] 支払い後に誰の点数も負にならない
- [x] 支払い者の残高が不足する場合、残高分だけを徴収する
- [x] **クランプが発生しても4人の点数の総和が変わらない**（点数保存則）
- [x] 支払いの内訳（誰が誰にいくら）が `Payment[]` として得られる（Step 4 の演出で使う）
- [x] `Payment` は `GameEvent` の `Paid` と同一の型を共有し、二重定義になっていない
- [x] 精算結果を `GameEvent[]` に変換するヘルパがあり、Step 3 が同じ変換を複数箇所に書かずに済む
- [x] `scores` の各要素が 0 以上であるという前提が明文化され、前提に反した入力でも点数保存則が破れない

## 成功指標

- Step 2 のテストが全件 PASS し、役判定と点数計算の不変条件がテストで固定されている
- Step 3（対局状態機械）が `findYaku` / `bestYaku` / `settleTsumo` / `settleRon` / `toPaidEvents` だけを前提に着手できる
- `computeWaits` は Step 4 のリーチ表示用であり **1手先（テンパイ）専用**。Step 3 の CPU AI が2手以上先のシャンテン評価をしたい場合は、これを転用せず列挙ロジックを参考に独自実装する
- エンジン層が React・`src/config/` に依存していない（`npm run lint` の `no-restricted-imports` で担保）

## スコープ外

以下はこのフェーズでは実装しません:

- 対局状態機械・フェーズ遷移・割り込み宣言の優先度解決（Step 3）
- CPU AI の思考（Step 3）
- 対局 UI・リーチ枠の描画・アニメーション（Step 4）
- BET・精算・所持コイン永続化（Step 5）
- 「ダマポカジャン」（役を伏せて同色を狙う戦術）の AI 実装（v2 以降）
