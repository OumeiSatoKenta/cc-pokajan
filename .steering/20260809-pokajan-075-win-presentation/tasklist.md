### 学んだこと

1. **「落ちることを確かめる」手順が、今回いちばん効いた。**
   「視覚効果を減らす設定では順位表が最初から和了後で出る」を書き、
   実装をわざと壊して走らせたら**通ってしまった**。調べると
   `test.use({ reducedMotion: 'reduce' })` がこの構成ではページに届いておらず
   （`matchMedia('(prefers-reduced-motion: reduce)')` が `false` のまま）、
   **減らす設定を検査したつもりで通常の経路を検査していた**。
   `page.emulateMedia()` に変え、さらに「設定がページに届いていること自体」を
   `data-reduced` で先に確かめるようにした。
   この手順が無ければ、**壊れていることに気づけないテストを1本増やして完了**していた。

2. **公式ドキュメントで API を確かめても、環境で効くかは別。**
   framer-motion の `layout` は Context7 で確認したとおりに動いた。
   一方 Playwright の `reducedMotion` は**ドキュメントどおりのはずが効かなかった**。
   ライブラリの使い方（正しさ）と、この環境での挙動（実際）は別に確かめる必要がある。

3. **抽出は「振る舞いが変わっていないこと」を検査して初めて抽出になる。**
   `computeRanking` の切り出しは3行の移動だが、順位はそのまま順位倍率＝
   **精算額**になる。`GameOver.ranking` が `computeRanking` の結果と一致することを
   固定して、同点（ID 昇順）まで含めて確かめた。ここが崩れると、
   演出の順位と精算の順位が違うという最も分かりにくい不一致が起こる。

4. **足したデータが使われないと分かったら、その場で外す。**
   `payments` は 7-4 で足したが、7-5 で「増減は前後の差分から出す」と決めた時点で
   読まれなくなった。1ステップで足して次で外すのは格好が悪いが、
   **使われないフィールドを残すほうが高くつく**（次に読む人が
   「これを使うべきか」を毎回考えることになる）。
   情報は失っていない——明細が要るなら `pending` の `Paid` から作り直せる。

### 検証中に一度だけ落ちた E2E について

`人間が宣言窓で迷っている間に CPU の意思表示が出揃う` が1回だけ失敗した。
**そのときは全67件の所要時間が 33秒 → 3分12秒（約6倍）**になっており、
`npm run build` 直後で dev サーバが再最適化していたことによる遅延と見ている。

単体で3回、全件で3回走らせ直したがいずれも通ったため、コードの回帰ではないと判断した。
この失敗は `discardFirst` が**クリックの失敗を握りつぶさない**設計（Step 4b）の帰結で、
極端に遅い環境では意図どおり「その場で失敗する」。握りつぶす方向へは直さない。
