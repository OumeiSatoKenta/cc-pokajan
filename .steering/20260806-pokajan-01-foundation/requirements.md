# 要求内容

## 概要

ポカジャン再現ウェブゲームの **Step 1（基盤・型定義・山札生成）** として、Vite(react-ts) でプロジェクトを初期化し、ドメイン型・シード付き乱数・山札構築・配牌を純粋 TypeScript で実装する。

対局 UI（TableScreen 等のゲーム画面）は実装せず、エンジンの正しさは Vitest によるテストで検証する。`src/App.tsx` は「Step 1 時点で何が動くか」を示すプレースホルダに留める。

## 背景

`cc-pokajan` は空のリポジトリであり、[docs/ideas/pokajan-plan.md](../../docs/ideas/pokajan-plan.md) の 6 ステップ計画のうち Step 1 が起点となる。

ポカジャンは「山札 100 枚」「1 ホロメン 9 枚（3 色 × 3 枚）」「グループ 4 つ / メンバー 12〜16 種」という独特の構成を持ち、**プール（108〜144 枚）から 100 枚だけを抜き出す**ため山札に入らないカードが存在する。この山札生成ロジックの正しさが後続の役判定・対局進行すべての前提になるため、UI に着手する前にテストで固めきる。

また、対局の再現性（リプレイ・テストの決定性）を担保するため、**エンジン内では `Math.random()` を使わずシード付き乱数のみを使う**方針を最初の段階で確立する。

## 実装対象の機能

### 1. プロジェクト基盤

- Vite(react-ts) テンプレートによるプロジェクト初期化
- `dev` / `build` / `test` / `lint` / `lint:fix` / `typecheck` / `format` スクリプトの整備
- `src/`（アプリ）と `tests/`（テスト）を分離した TypeScript プロジェクト参照構成
- 開発者が `npm install` 後すぐに `npm test` / `npm run dev` を実行できる

### 2. ドメイン型定義（`src/engine/types.ts`）

- カード・メンバー・グループ・ロスター・役候補・プレイヤー・対局状態・アクション・イベントの型
- Step 2 以降（役判定・状態機械）が参照する共通語彙を確定させる

### 3. シード付き乱数（`src/engine/rng.ts`）

- mulberry32 による決定的 PRNG と Fisher–Yates シャッフル
- 同一シードから常に同一の結果が得られ、テストとリプレイの再現性を担保する

### 4. ルール設定（`src/config/rules.ts`）

- 手札枚数・山札枚数・点数表・BET 設定など全ての可変数値を 1 ファイルに集約
- 実機未確認の値には `TODO(要実機確認)` を明示し、後から 1 箇所の変更で追随できる

### 5. デフォルトロスター（`src/config/defaultRoster.ts`）

- オリジナルの仮キャラ 6 グループ / 24 名（サイズ 3,3,4,4,5,5）
- 公式素材を一切含まず、画像なしでも成立する

### 6. 山札構築・配牌（`src/engine/deck.ts`）

- ロスター検証 → グループ選出 → カードプール構築 → 100 枚抽出 → ボーナス選出 → 配牌
- 不正なロスターを検証段階で弾き、山札が組めない状態に陥らせない

## 受け入れ条件

### プロジェクト基盤

- [ ] `npm install` が成功する
- [ ] `npm run build` が 0 エラーで完了する
- [ ] `npm run typecheck` が `src/` と `tests/` の両方を検査して 0 エラー
- [ ] `npm run lint` が 0 エラー
- [ ] `npm test` が実行でき、全テストが PASS する
- [ ] `npm run dev` で開発サーバが起動する
- [ ] 表示される画面が Vite テンプレートのデモ内容（カウンターボタン・ロゴ等）を含まず、Step 1 時点の実装状況が読み取れる
- [ ] プレースホルダ画面が `setupGame` の結果を表示し、ブラウザ上でもエンジンが動作することを確認できる
- [ ] `src/engine/` と `src/config/` から `react` を import すると `npm run lint` がエラーになる（手動確認ではなく lint ルールで恒久的に担保する）

### ドメイン型定義

- [ ] `Card` / `Member` / `Group` / `Roster` / `YakuCandidate` / `Player` / `GameState` / `Action` / `GameEvent` が定義されている
- [ ] `YakuContext`（`activeGroups` / `bonusMemberIds` / `rules`）が定義され、Step 2 の `findYaku(hand, ctx, required?)` がそのまま書ける契約になっている
- [ ] `RulesConfig` / `YakuScore` / `BetConfig` が定義され、エンジン層が `src/config/` を import せずに済む
- [ ] `ColorId` が 3 色（pink / blue / orange）に制約されている
- [ ] 型定義に実装ロジックを含まない（型のみのモジュール）

### シード付き乱数

- [ ] 同一シードから生成した乱数列が完全に一致する
- [ ] 異なるシードでは異なる乱数列になる
- [ ] 生成値が常に `0 <= x < 1` の範囲に収まる
- [ ] `shuffle` が入力配列を破壊せず、要素の多重集合が保存される
- [ ] `shuffle` が同一シードで同一結果を返す

### ルール設定

- [ ] 調査で判明した点数（3カード120 / 3人組180 / 4人組300 / 5人組480 / 同色3カード840 / 同色4人組840 / 同色5人組1800 / ボーナス+90）が反映されている
- [ ] 未確定値に `TODO(要実機確認)` コメントがある。具体的には **`group3.sameColor` = 540（180 × 3 の推定値）** と **`startingScore` = 1000（精算例からの推定値）** の 2 箇所
- [ ] 全ての役の点数が 3 で割り切れる（ツモ 1/3 分配を整数演算で行うための前提）

### デフォルトロスター

- [ ] 6 グループ / 22 メンバー（サイズ 3, 3, 3, 4, 4, 5）で構成されている
- [ ] グループサイズが 3〜5 の範囲に収まり、3 サイズすべてを含む（3人組・4人組・5人組の全役が出現しうる）
- [ ] 4 グループ選出時の合計人数が 13〜16 人に収まる（原作の実測レンジ 12〜16 種とほぼ一致する）
- [ ] 1 メンバーが複数グループに重複所属していない
- [ ] 全メンバーに `accent` カラーが設定されている（画像未設定でもカードを描画できる）
- [ ] `validateRoster` を通過する

### 山札構築・配牌

- [ ] `buildDeck` が常にちょうど `deckSize`（100）枚を返す
- [ ] 1 メンバーあたりのカードが 9 枚以下、1 メンバー 1 色あたり 3 枚以下
- [ ] 全カードの `uid` が一意
- [ ] 山札の全カードが選出グループのメンバーのものだけで構成される
- [ ] 同一シードで完全に同一の山札が生成され、異なるシードでは異なる
- [ ] `selectGroups` が重複なくちょうど 4 グループを返す
- [ ] `selectBonusMembers` が **山札に実際に含まれるメンバー**の中から重複なく指定数を返す（あるメンバーの 9 枚すべてが山札外に落ちて「一度も引けないボーナス」になるのを防ぐ）
- [ ] `deal` が 4 人へ 7 枚ずつ配り、残り壁が 72 枚になる（100 − 28）
- [ ] 配牌後、手札と壁の全カードを合わせると元の山札と完全に一致する（カードの消失・複製がない）
- [ ] `validateRoster` が不正ロスター（グループ数不足 / サイズ範囲外 / 未知メンバー / 重複所属 / プール不足）を全て検出する

## 成功指標

- Vitest のテストが全件 PASS し、山札生成に関する不変条件がテストで固定されている
- Step 2（役判定）が本 Step の型と `deck.ts` の出力だけを前提に着手できる
- エンジンのコードが React に一切依存していない（`src/engine/` と `src/config/` から React の import が 0 件）

## スコープ外

以下はこのフェーズでは実装しません:

- 役判定・点数計算・支払い処理（Step 2）
- 対局状態機械・CPU AI（Step 3）
- 対局 UI・アニメーション（Step 4）
- BET・精算・所持コイン永続化（Step 5）
- ロスターエディタ・画像アップロード・ルール設定画面（Step 6）
- `framer-motion` / `@playwright/test` の導入（実際に利用する Step 4 で追加する）
