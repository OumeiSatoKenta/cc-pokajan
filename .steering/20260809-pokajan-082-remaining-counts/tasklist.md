### 計画と実績の差分

| 項目 | 計画 | 実際 | 理由 |
| ---- | ---- | ---- | ---- |
| 引き当ての関数 | `unseenOf` の1つ | **`colorCountsOf` を足して2つ** | ツールチップは全色、待ち一覧は1色。どちらも見つからなければ例外 |
| 待ち一覧の並び | 点数降順 | **残っている待ちが先、その中で点数降順** | 下記2 |

| E2E の進行ヘルパ | `playUntil` を足す | **`advanceOneStep` を抽出して3つのループで共有** | 3つ目のループを足すと手順の写しが3つになる |
| 既存 E2E | 触らない | **1件直した** | 下記4 |

### 学んだこと

1. **`expect` は検査ではなく計測対象になることがある。**
   突き合わせを素直に `onStep` の中で `expect` すると、100局 × 約600ステップ ×
   4人 × 66通りで**1600万回**を超え、5秒のタイムアウトに引っかかった（実測45秒）。
   食い違いを配列に集めて最後に1度だけ `expect` する形にしたら **1.3秒**になった。
   **集める形にしても検査の強さは落ちない**ことは、河と成立済みの役を
   それぞれ数えない壊し方で確かめてある。

2. **「上位N件」と「死んだ行を淡くする」は素直に組むと噛み合わない。**
   計画では点数降順だったが、それだと**高い役の待ちが全部死んでいる局面で、
   生きている待ちが「他N件」の下に隠れる**。淡く落とす行が中心的な価値なのに、
   そもそも表示されない。生死を第1キーにして解決した。
   打ち切りを入れるときは「切り捨てられる側に価値がないか」を必ず見る。

3. **わざと壊す手順が、また「何も見ていないテスト」を捕まえた（3回目）。**
   「自分の手番でなくても残り枚数を調べられる」は、ホバーの受け口を
   `CardView` に移す壊し方で**通ってしまった**。原因は
   **マウスが動かなければ `mouseleave` は起きない**こと。押せた頃に出した
   ツールチップが残っているだけの状態を「出ている」と読んでいた。
   毎回いったん手札の外へ出し、**消えたことを確かめてから掛け直す**形にしたら落ちるようになった。

4. **同じボタンが2つの判断に使われているなら、ボタンで進行を観測しない。**
   既存の `人間が宣言窓で迷っている間に…` が6回中3回落ちることが分かった
   （Step 8-2 とは無関係の既存の不安定さで、ヘルパを元の形に戻しても同率で落ちた）。
   「見送るボタンが消える」で受付の終了を見ていたが、このボタンは
   **割り込みの見送りと宣言の見送りの両方**に使われる。進行が正しく再開して
   次の機会が来ればボタンは戻る。「割り込みタイマーが消える」も同じ理由で使えない
   （次の捨て札ですぐ新しい受付が開く）。**山札の残りだけが一方向に動く**ので、
   それで見るようにしたら8回連続で通った。8-1 の教訓の続き。

5. **式の言葉を閉じた形で定義する。** 着手前レビューが
   「場の全カード」という語の曖昧さを指摘した。山札を含む読み方と含まない読み方があり、
   含まない読み方で実装すると**山札が枯れる終局間際にだけ一致に近づく**ため、
   落ちたり通ったりするテストになっていた。`inDeck(m,c)` と `notInDeck(m,c)` を
   定義してから書いた。Step 3 に続き、着手前レビューが式の誤りを捕まえた2例目。

6. **「消えたか」を種類で判定すると、同じ種類の別物で復活する。**
   ホバー状態をメンバー単位で持ち「そのメンバーが手札に居るか」で消していたが、
   捨てたあとに**同じメンバーの別の札**を引くとツールチップが独りでに戻ってきた
   （欠陥レビューが発見）。消えたことを見たいなら、消えうる単位そのもの
   （ここでは `uid`）で持つ。1局を通じて一意なので、戻ってくることがない。

7. **目視は「それらしく見える」で止めない。**
   スクリーンショットのカードの色を目で読んで残枚数を検算しようとして間違えた。
   実際の手札を出力して突き合わせたら表示のほうが正しかった。
   **絵を見て数えるくらいなら、真の値を出力して比べる。**

### 3軸コードレビューの結果と対応

| 軸 | 評価 | `[必須]` |
| ---- | ---- | ---- |
| 構造・アーキテクチャ | A / A / A / B / A | 0件 |
| 欠陥・セキュリティ | B / B / A / A / B | **1件** |
| API・ドキュメント準拠 | 問題なし4件・推奨1件・提案1件 | 0件 |

**[必須] ホバー状態をメンバー単位で持っていた（`Hand.tsx`）。**
`useState<MemberId>` だったため、次の順で**マウスを動かしていないのにツールチップが
勝手に戻ってくる**。(1) a1 にホバー → (2) その a1 を捨てる（`mouseleave` は起きない。
表示は「手札に a1 が居ない」ので消える）→ (3) 数手後に別の a1 を引く →
(4) 判定が再び真になり復活。**`uid` で持つ形に直した**。uid は1局を通じて一意で、
消えた札は戻らない。自分で書いた「手札と突き合わせる」という対策が、
**同じキャラの別の札**という抜け道を持っていた。

対応した推奨:

- **突き合わせを既定値以外のルールでも回す**（3人・2色・1枚・`deckSize` 24）。
  「3色・3枚のときだけたまたま合う」実装を取りこぼさないため。壊して落ちることも確認済み
- **`WaitPanel` の境界を2件追加**（ちょうど上限で「他0件」を出さない / 全滅時も一覧は消えない）
- **`role="status"` → `role="tooltip"` + `aria-describedby`**（`CardCounts` / `CardView` / `Hand`）。
  `role="status"` は暗黙の `aria-live` を持つため、**マウスを乗せただけで読み上げが割り込む**。
  焦点を当てた札だけがツールチップを指すようにした
- **`tests/engine/unseen.test.ts` を分割**（430 行になったため）。
  構造の検査と自動対局との突き合わせで分け、土台は `tests/helpers/unseen.ts` へ。
  **レビュー対応でテストが増えた分も測り直す**（フェーズの区切りだけで測ると見落とす）
- **待ちの集合と数える集合の一致をテストで固定**（構造レビューの `[質問]`）。
  `computeWaits` は `activeGroups` から、`countUnseen` の呼び出し側は `activeMembers` から
  メンバーを作る。崩れると `unseenOf` が例外を投げて画面ごと落ちるのに、
  2つの離れたモジュール間の暗黙の合意にしか支えられていなかった

見送った指摘（理由つき）:

| 指摘 | 見送りの理由 |
| ---- | ---- |
| `sortRows` を `waitOrder.ts` へ分離 | 8行。壊す検査で回帰は捕まえられている。指摘者も「必須ではない」 |
| `game.ts` の再エクスポートが未使用 | `yakuContextOf` と同じ既存の慣習。今回の範囲でバレルの方針を変えるのは筋が違う |
| `maxRows` に負値のガード | 呼び出し元は既定値のみ。`Math.max` で黙って正規化するのは「不正な入力を黙って無視しない」に反する |
| `onMouseEnter` → `onHoverStart` | 触れる端末で**出なくなる**。今は出たほうがまし（触れる端末の対応は v2） |
| `SEEDS` の定義が2ファイルに重複 | 1行。共有ヘルパにするほどではない |

**[質問] への回答**: テンパイしておらず自分の手番でもないとき、キーボードだけの
利用者が残枚数を確認する手段は無い。これは**意図的な範囲外**（計画の

解決するには手札の焦点の持たせ方そのものを変える必要があり、8-2 の範囲を超える。
