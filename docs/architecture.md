# 技術仕様書 (Architecture Design Document)

本書は [product-requirements.md](product-requirements.md) と
[functional-design.md](functional-design.md) を技術的に実現するための構造と技術選定を定義する。

**本アーキテクチャを貫く1つの判断**: **サーバーを持たない。**
CPU 対戦のみで通信の必要がなく、実在人物の顔写真を扱うプライバシー要件があり、
静的ホスティングだけで配布できる。この判断がストレージ・セキュリティ・
スケーラビリティのすべての設計を規定している。

## テクノロジースタック

### 言語・ランタイム

| 技術       | バージョン | 備考                                       |
| ---------- | ---------- | ------------------------------------------ |
| Node.js    | v25.9.0    | 開発時のみ。成果物の実行には不要           |
| TypeScript | ~6.0.2     | `strict` / `verbatimModuleSyntax` を有効化 |
| npm        | 11.12.1    |                                            |

**実行環境**: モダンブラウザ（ES2023 + IndexedDB + Canvas をサポートするもの）。
成果物は静的ファイルのみで、サーバーサイドのランタイムを必要としない。

### フレームワーク・ライブラリ

| 技術          | バージョン | 用途                     | 選定理由                                                                     |
| ------------- | ---------- | ------------------------ | ---------------------------------------------------------------------------- |
| React         | ^19.2.8    | UI の宣言的な描画        | 状態から UI を導出する形がエンジンのリデューサと素直に噛み合う                |
| react-dom     | ^19.2.8    | DOM への描画             | React の対                                                                   |
| framer-motion | 導入予定   | カードのアニメーション   | FLIP を自前実装せずに済む。**対局画面でのみ import** しバンドル影響を局所化   |

**採用しなかったもの**:

| 技術                          | 不採用の理由                                                                 |
| ----------------------------- | ---------------------------------------------------------------------------- |
| 状態管理ライブラリ（Redux 等）| 画面数が6つで状態も単純。`useReducer` + Context で足りる                     |
| ルーティングライブラリ        | URL を持たない単一ページ。`useReducer` の画面ステートマシンで足りる           |
| UI コンポーネントライブラリ   | カードゲーム特有の見た目が必要で、汎用部品の恩恵が小さい                     |
| i18n ライブラリ               | 日本語固定。多言語化は要件に入っていない                                     |
| HTTP クライアント             | **通信を行わないため不要**                                                   |

| --------------- | ---------- | ---------------- | ------------------------------------------------------------------- |

## アーキテクチャパターン

### レイヤードアーキテクチャ（依存は一方向）

```
┌──────────────────────────────────────────────┐
│  UI レイヤー  src/ui/, src/App.tsx            │ ← 入力の受付・描画・時間の管理
├──────────────────────────────────────────────┤
│  永続化レイヤー  src/storage/                  │ ← localStorage / IndexedDB
├──────────────────────────────────────────────┤
│  設定レイヤー  src/config/                     │ ← ルール値・同梱ロスター
├──────────────────────────────────────────────┤
│  エンジンレイヤー  src/engine/                 │ ← ゲームロジック（純粋TS）
└──────────────────────────────────────────────┘
        ↑ 依存の向きは常に下から上へは向かない
```

#### エンジンレイヤー（`src/engine/`）

- **責務**: ゲームのルールそのもの。役判定・状態遷移・精算・CPU 思考
- **許可される操作**: 同レイヤー内の他モジュールの呼び出し
- **禁止される操作**:
  - React / DOM への依存
  - `src/config/` への依存（ルール値は**引数で受け取る**）
  - `Math.random()` / `Date` の使用
  - 副作用（I/O・ストレージアクセス・ログ出力）

> **この制約は機械的に担保される。** `.oxlintrc.json` の `no-restricted-imports` が
> `src/engine/**` からの `react` / `react-dom` / `**/ui/**` / `**/config/**` の
> import を禁止し、`npm run lint` が違反を検出する。
> ルールを文書に書くだけでは守られないため、静的解析に落としている。

#### 設定レイヤー（`src/config/`）

- **責務**: 可変な数値（ルール値）と同梱ロスターの提供
- **許可される操作**: `src/engine/types.ts` の型を参照する
- **禁止される操作**: エンジンのロジック呼び出し、React への依存

型は `engine/types.ts`、値は `config/rules.ts` に置く。
**型と値を分けることで、エンジンが設定層に依存せずに済む。**

#### 永続化レイヤー（`src/storage/`）

- **責務**: ブラウザストレージへの読み書き
- **許可される操作**: localStorage / IndexedDB へのアクセス
- **禁止される操作**: ゲームロジックの実装、**ネットワーク通信**、UI 層の参照

**保存するのは残高だけで、精算額や順位は保存しない。** 計算結果を保存すると、
localStorage を書き換えるだけで所持コインを増やせる経路が増える。
精算はその都度 `engine/payout.ts` が計算する。

**読み書きは外部入力として扱う。** ユーザーが直接編集でき、別バージョンの本アプリが
書いた値が残っていることもあり、プライベートモードではアクセス自体が例外になる。
`loadPrefs` / `savePrefs` は例外を投げず、読めない値は既定値へ倒す。

依存の向きは `.oxlintrc.json` の `no-restricted-imports` で機械的に守っている
（エンジン → storage も禁止）。

#### UI レイヤー（`src/ui/`, `src/App.tsx`）

- **責務**: 入力の受付、描画、アニメーション、**時間の管理**
- **許可される操作**: 全レイヤーの呼び出し
- **禁止される操作**: ゲームルールの再実装（判定はエンジンに委ねる）

**時間を UI 層が持つのが本設計の要点**。宣言の受付時間は UI が `TICK(deltaMs)` として
エンジンへ供給する。エンジンが時計を持たないため、対局の全経過が
「初期シード + アクション列」だけで完全に再現できる。

### 状態機械 + イベント発行パターン

エンジンは `reduce(state, action, rules) => { state, events }` の純粋関数として実装する。
状態と一緒に演出用の `GameEvent[]` を返すことで、**ロジックとアニメーションを疎結合**にする。

```
UI                          エンジン
 │  dispatch(action)          │
 ├──────────────────────────► │
 │                            │ 純粋な計算（副作用なし）
 │  { state, events }         │
 │ ◄──────────────────────────┤
 │                            │
 ├─ state → 描画               │
 └─ events → アニメーション再生 │
```

UI がフェーズをポーリングして演出を組み立てるのではなく、
**返却されたイベント列を見る**。過渡フェーズ `resolveClaim` は `reduce` の
戻り値には現れないため、フェーズだけを見ていると割り込みの発生を検知できない。

### 情報遮断パターン（CPU AI）

CPU は `GameState` を受け取らず、公開情報だけを含む `AiView` を受け取る。
`toAiView(state, playerId, rules)` が `GameState` に触れる唯一の場所であり、
他家の手札や山札の中身へ到達する経路が**型として存在しない**。

これは「AI が不正しないよう気をつける」という規律ではなく、
**不正できない構造**にすることで担保している。

## データ永続化戦略

### ストレージ方式

| データ種別               | ストレージ    | フォーマット      | 理由                                                       |
| ------------------------ | ------------- | ----------------- | ---------------------------------------------------------- |
| 所持コイン・ルール上書き | localStorage  | JSON（単一キー）  | 小さく、同期的に読めるほうが起動が単純                     |
| ロスター定義             | localStorage  | JSON（同上）      | 数KB程度。画像 ID のみを持ち、実体は持たない               |
| **キャラクター画像**     | **IndexedDB** | **Blob**          | localStorage の約5MB制限では20人分の写真が入らない         |
| 対局中の `GameState`     | **保存しない**| —                 | リロードで破棄。中断復帰は Post-MVP                        |
| ロスターの書き出し       | ファイル      | JSON（base64画像）| 依存ライブラリなしで入出力でき、1ファイルで受け渡しできる  |

**localStorage キー**: `cc-pokajan:prefs`
**IndexedDB**: DB名 `cc-pokajan` / ストア `assets`（keyPath: `imageId`）

保存形式には `version` を持たせ、一致しなければ移行せず既定値で起動する
（移行の分岐は必要になった時点で足す）。内容は次のとおり。

```ts
{
  version: 1,
  wallet: number,
  lastSeed: number,
  roster: Roster | null,              // 未設定なら同梱ロスター
  rulesOverride: Partial<RulesConfig> | null,  // **差分**で持つ
}
```

**ルールは差分で保存する。** 全体を保存すると、既定値を変更したときに古い保存値が
全項目を上書きし続け、更新が利用者に届かなくなる。差分なら触っていない項目は
常に最新の既定値に追随する。

### 保存値とエンジンの境界（重要）

保存されたロスターとルールは**そのままエンジンに渡る**。localStorage はユーザーが
直接編集でき、別バージョンの本アプリが書いた値も残る。`handSize: 0` のような値が
入ると配牌の時点で例外になり、永続化されているぶんリロードしても回復しない
（＝**タイトル画面すら出せなくなる**）。

`src/appSettings.ts` の `resolveSettings` が採用の可否を決め、通らなければ既定値に倒す。
判定は3段構えにしている。

| 検査                            | 目的                                                     |
| ------------------------------- | -------------------------------------------------------- |
| `validateRules`                 | 構造的な誤り。画面に理由を出すため                       |
| `validateRoster`                | ロスターの妥当性                                         |
| `canStartGame`（実際に初期化）  | **列挙し切れないルール×ロスターの組み合わせ**を捕まえる  |

3つ目が要るのは、`bonusMemberCount` の上限のようにルール単体では判定できない項目が
あるため。検査項目の列挙に正しさを預けず、**「実際に始められること」自体**を条件にする。
逆に `handSize: 0` / `playerCount: 0` は `createGame` が例外にしないため
`canStartGame` を通り抜ける。1つ目と3つ目は互いの穴を塞ぎ合っている。

### バックアップ戦略

**自動バックアップは行わない。** サーバーを持たず、データはユーザーの端末にのみ存在する。
代わりに以下で対応する。

- **手動エクスポート**: ロスターを画像込みの単一 JSON ファイルとして書き出せる。
  これが実質的なバックアップ手段であり、同時に共有手段でもある
- **復元方法**: 書き出したファイルを読み込む。`validateRoster` を通してから保存する
- **破損への耐性**: localStorage の読み込みに失敗した場合は既定値で起動する
  （エラーで起動不能にしない）

> **利用者への明示が必要**: ブラウザのデータ削除でロスターと所持コインは失われる。
> 大事なロスターは書き出しておくよう UI で案内する。

## パフォーマンス要件

### レスポンスタイム

| 操作                       | 目標時間  | 測定環境                     | 実測         |
| -------------------------- | --------- | ---------------------------- | ------------ |
| 自動対局100局              | 1秒以内   | Vitest（Node）               | **63ms**     |
| 役判定・待ち計算（1手番）  | 10ms以内  | 同上                         | 1ms未満      |
| カードクリック → 描画反映  | 100ms以内 | 一般的な PC / スマートフォン | Step 4 で測定 |
| 初期表示（TTI）            | 2秒以内   | 一般的な回線                 | Step 4 で測定 |
| 画像アップロード → 反映    | 1秒以内   | 1枚あたり                    | Step 6 で測定 |

### リソース使用量

| リソース         | 上限            | 理由                                                     |
| ---------------- | --------------- | -------------------------------------------------------- |
| バンドル（gzip） | 150KB           | 低速回線でも初期表示が2秒以内に収まる目安                |
| localStorage     | 1MB             | ロスター定義のみ（画像を含めない）。制限5MBに対し十分な余裕 |
| IndexedDB        | 30MB            | 256×256 webp を1枚〜30KB として、最大1000枚相当           |
| メモリ           | 明示的な上限なし | 対局中の状態は数百枚のカードのみで、実質的な制約にならない |

**現在のバンドルサイズ**: 218.78 kB / gzip 69.53 kB（Step 3 時点、framer-motion 未導入）

## セキュリティアーキテクチャ

### データ保護

- **暗号化**: 行わない。データは端末外に出ないため、通信路の保護対象が存在しない。
  ブラウザストレージの暗号化は OS / ブラウザの領域とする
- **アクセス制御**: 同一オリジンポリシーに依存する。認証機構は持たない（単一利用者前提）
- **機密情報管理**: **アプリケーションが保持する秘密情報は存在しない**。
  API キー・トークン・接続文字列を持たない設計

### 通信

**外部への通信を行わない。** これは方針であると同時に**構造**でもある。

- `fetch` / `XMLHttpRequest` / WebSocket を使うコードを実装しない
- 外部 CDN からのフォント・スクリプト読み込みを行わない（全て自前バンドルに含める）
- テレメトリ・アナリティクスを組み込まない

**この構造により、実在人物の顔写真が流出する経路が存在しない。**
「送信しないよう注意する」ではなく「送信するコードがない」ことで担保する。

### 入力検証

| 検証対象               | 方法                                                                     |
| ---------------------- | ------------------------------------------------------------------------ |
| ロスターファイル       | `validateRoster` が構造から検証。壊れた JSON でも例外ではなくエラー一覧を返す |
| アップロード画像       | canvas で 256×256 webp に**再エンコード**。元のメタデータやペイロードは残らない |
| 宣言された役           | 信用せず `findYaku` で**再計算した候補に置き換える**（点数偽装が原理的に効かない） |
| アクション             | フェーズ・プレイヤー ID・カードの所持を検査し、違反は `IllegalActionError` |
| ルール値               | 役判定の対応範囲（グループ3〜5人）を外れる設定を対局開始前に弾く         |
| メンバー名の表示       | React の既定のエスケープ。`dangerouslySetInnerHTML` を使わない           |

**エラー表示の方針**: 利用者の入力ミス（壊れたロスター）は具体的な内容を表示する。
内部の不変条件違反は例外として送出し、**黙って無視しない**。

## スケーラビリティ設計

### データ増加への対応

| 想定                     | 対応                                                             |
| ------------------------ | ---------------------------------------------------------------- |
| 20〜30人規模の組織       | 画像は IndexedDB のため容量制限に当たらない                      |
| グループ数の増加         | 1局に登場するのは `groupsPerGame`(4) 個のみ。ロスター全体が増えても対局の計算量は変わらない |
| 1メンバーあたりのカード  | `colors × copiesPerMemberColor` = 9枚で固定                       |
| 画像1枚の容量            | アップロード時に 256×256 webp へ縮小（〜30KB）                    |

**計算量の観点**: 対局中の処理はすべて「今局の登場メンバー（12〜16人）」に閉じており、
ロスター全体のサイズに依存しない。ロスターが100人になっても対局の速度は変わらない。

### 機能拡張性

| 拡張                 | 必要な変更                                                                 |
| -------------------- | -------------------------------------------------------------------------- |
| 役の種類を追加       | `YakuKind` に追加、`rules.scores` にエントリ追加、`findYaku` に列挙を1つ追加 |
| カードの色数を変更   | `rules.colors` を変更するだけ。`yaku.ts` の変更は不要                       |
| プレイヤー数を変更   | `rules.playerCount` を変更。`reduce` が状態との整合を入口で検査する         |
| ルール値の調整       | `RulesConfig` を差し替えるだけ。全エンジン関数が引数で受け取る              |
| CPU の強さ           | `AiConfig`（patience / safety）のプリセット追加                            |
| 対局のリプレイ       | シード + アクション列で再現可能。`rngState` を保持済み（土台は既にある）    |

**プラグインシステムは持たない。** 拡張は上記のとおり設定値と型の追加で足りる規模であり、
動的なプラグイン機構は複雑さに見合わない。

### 設定のカスタマイズ範囲

| 項目                       | ユーザーが変更可能か   |
| -------------------------- | ---------------------- |
| メンバー・グループ・画像   | ✅ ロスターエディタ    |
| 点数表・初期点・BET設定    | ✅ ルール設定画面      |
| 手札枚数・山札枚数         | ✅ ルール設定画面      |
| CPU の難易度               | ✅ 設定               |
| 役の種類そのもの           | ❌ コード変更が必要    |

## テスト戦略

### ユニットテスト

- **フレームワーク**: Vitest 4（環境は `node`。DOM が必要な箇所は `renderToStaticMarkup` で代替し、
  jsdom を導入していない）
- **対象**: `src/engine/**` の全モジュール、`src/config/rules.ts` の制約
- **カバレッジ目標**: **数値目標を設けない。** 代わりに「不変条件が検査されていること」を基準とする

> **カバレッジを目標にしない理由**: Step 2 で、186件のテストが全て通っている状態で
> 実在の欠陥が3件見つかった。行が実行されたことと正しいことは別である。
> 構造的整合性のテストは「候補に入っているものの正しさ」しか見ておらず、
> **本来成立すべき役の取りこぼし（偽陰性）を検出できない**。
> そのため重要なロジックには**素朴な別実装との突き合わせ**を用意する方針を採る。

### 統合テスト

- **方法**: 全員 CPU の自動対局（`playGameToEnd`）を、シードを変えて100局実行する
- **対象**: 状態機械と AI の結合、および対局全体の不変条件
- **検査項目**（**全局・全ステップ**で検査）:
  - 点数保存則: 4人の合計点が `startingScore × playerCount` から変化しない
  - カード保存則: 山札 + 手札 + 河 + 成立済みの役 = `deckSize`、`uid` に重複なし
  - 手札枚数: `expectedHandSize` と一致する
  - 山札の単調減少 / 過渡フェーズが外部に漏れないこと
- **統計回帰**: 終了理由の内訳・平均打牌数が実測レンジに収まること（AI 変更時の破綻検知）

### E2Eテスト

- **ツール**: Playwright（Step 4 で導入）
- **シナリオ**:
  - 対局画面で1局を最後まで進め、終了状態に到達する
  - BET → 対局 → 精算 → ウォレット反映のループ
  - 画像をアップロードし、リロード後も保持される
  - 書き出したロスターを別コンテキストで読み込んで対局できる

### 検証ゲート

各作業の完了条件として以下を全て通す。

```bash
npm run lint && npm run typecheck && npm test && npm run build && npm run format:check
```

## 技術的制約

### 環境要件

- **実行環境**: モダンブラウザ（Chrome / Firefox / Safari / Edge の最新2バージョン）
- **必要な Web API**: IndexedDB、Canvas（`toBlob` の webp 対応）、File API、localStorage
- **開発環境**: Node.js LTS 以降、npm
- **必要な外部依存**: **なし**（実行時にサーバー・API・データベースを必要としない）
- **オフライン動作**: 初回読み込み後はオフラインで動作する（Service Worker は未導入）

### パフォーマンス制約

- 自動対局100局が1秒以内に完了すること（回帰テストとして日常的に回せる速度を保つ）
- 対局中の役判定が同期的に完了すること（Web Worker を使わない前提の計算量に収める）
- framer-motion を対局画面以外に持ち込まないこと

### セキュリティ制約

- **外部通信を実装しない**（構造的な制約）
- **公式の著作物をリポジトリに含めない**
- ユーザーがアップロードした画像を端末外へ出さない
- 秘密情報を保持しない（`.env` を使う場面が存在しない）

### 既知の制約と割り切り

| 制約                                 | 割り切りの理由                                                   |
| ------------------------------------ | ---------------------------------------------------------------- |
| ブラウザのデータ削除でデータが消える | サーバーを持たない以上避けられない。書き出し機能で代替する       |
| 端末間で自動同期されない             | 同上。ファイルの受け渡しで代替する                               |
| 対局の中断復帰ができない             | 1局が3〜7分で完結するため、優先度が低い                          |
| 未確定のルール値がある               | `TODO(要実機確認)` を付け、設定から1箇所の変更で追随できるようにする |

## 依存関係管理

| ライブラリ           | 用途                 | バージョン管理方針                                       |
| -------------------- | -------------------- | -------------------------------------------------------- |
| react / react-dom    | UI                   | `^` 範囲指定（マイナー更新を許容）                       |
| typescript           | 型検査               | `~` 範囲指定（**パッチのみ**。マイナー更新は挙動が変わりうる） |
| vite / @vitejs/plugin-react | ビルド        | `^` 範囲指定                                             |
| vitest               | テスト               | `^` 範囲指定                                             |
| oxlint / prettier    | 静的解析・整形       | `^` 範囲指定                                             |
| framer-motion        | アニメーション（予定）| `^` 範囲指定。**対局画面でのみ import**                  |
| @playwright/test     | E2E（予定）          | `^` 範囲指定                                             |

### 依存を増やす際の判断基準

1. **既存の依存で実現できないか**を先に検討する
2. 実行時依存（`dependencies`）は特に慎重に。バンドルサイズに直結する
3. **エンジンレイヤーには実行時依存を追加しない**。純粋 TS のまま保つ
4. 追加する場合は用途を本書の表に記録する

**現在の実行時依存は react / react-dom の2つのみ**（framer-motion を除く）。
ゲームロジック全体が外部依存ゼロで動作する。
