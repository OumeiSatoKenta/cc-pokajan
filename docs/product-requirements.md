# プロダクト要求定義書 (Product Requirements Document)

## プロダクト概要

### 名称

**ポカジャン（cc-pokajan）** - 好きなメンバーで卓を作れるカードゲーム

「ホロライブドリームス（ホロドリ）」のカジノミニゲーム **「ポカジャン！」** のルールを再現した、
1人 + CPU3人で遊ぶウェブゲーム。**ルールの出自は原作にあるが、遊ぶのに原作の知識は一切必要ない。**

### プロダクトコンセプト

- **カードの中身を自分たちで決められる**: メンバーとグループはすべてユーザーが定義する。
  同梱するのはオリジナルの創作キャラだけで、部署・チーム・friends など任意の集団に置き換えられる。
  **「自分たちだけの卓」を作れることが本プロダクトの中心的な価値**
- **ルールだけで面白い**: 「和了しても局が終わらない」という独特のルールを持つ打点レース。
  キャラクターを知らなくても、役と点数の仕組みだけで成立する
- **完全にクライアントサイドで完結**: サーバー・アカウント登録・通信を一切必要としない。
  アップロードした写真は端末から出ないため、実在の人物の画像でも安心して使える

### プロダクトビジョン

ポカジャンは「同じメンバー3枚」または「グループ全員を1枚ずつ」の2種類しか役がない、
極めてシンプルなルールのゲームである。にもかかわらず、和了しても局が終わらず打点レースが延々と続くため、
最後まで逆転の目が消えない。**このルールの面白さは、カードに何が描かれているかに依存しない。**

本プロダクトは、そのルールをブラウザ上で再現したうえで、
**カードの中身をまるごとユーザーに開放する**ことを目指す。
部署のメンバーを4つのチームに分けてカード化すれば、それは自分たちの組織だけのゲームになる。
サークルでも、家族でも、架空のキャラクターでも同じことができる。

素材は端末内に留まり外部へ送信されないため、実在の人物の写真を使っても情報が漏れない。
作ったロスターは1つのファイルとして書き出せるので、幹事が用意して全員に配る使い方が成立する。

### 目的

- ポカジャンのルールを、公開情報から確認できる範囲で正確に再現する
- **カードの中身（メンバー・グループ・画像）を完全にユーザー定義にする**
- 作ったロスターを他の人へ配布・共有できるようにする
- 対局ロジックの正しさを、目視ではなく**自動テストの不変条件**として証明する
- 未確定のルール値を設定として分離し、後から判明した値へ低コストで追随できるようにする
- 公式の著作物を一切同梱せず、素材はユーザーが用意する構造にする

## ターゲットユーザー

**前提**: いずれのペルソナも**ホロライブおよび原作ゲームに関心がない**。
原作の知識がなくても成立することが、ターゲット設定の出発点になっている。

### プライマリーペルソナ: 高橋健（35歳、ソフトウェアエンジニア）

- 麻雀・ドンジャラ系のルールを持つ軽量なブラウザゲームを探している
- ホロライブは名前を聞いたことがある程度で、原作は未プレイ。**ルールそのものの面白さ**に惹かれている
- **現在の課題**: 「和了しても局が終わらない」という珍しいルールを試せる実装が見当たらない。
  また、既存のカードゲームは絵柄が固定で、身内で遊ぶときの盛り上がりに欠ける
- **期待する解決策**: キャラクターを知らなくても、画面を見れば役と点数の仕組みが理解できること。
  カードの絵柄を自分で差し替えられること
- **1日の典型的な使い方**: PC のブラウザで数局試し、気に入ったら身内用のロスターを作る

### セカンダリーペルソナ: 中村あかり（41歳、20人規模のチームのマネージャー）

- 半期に一度のチーム懇親会で使える、**メンバー全員が登場する出し物**を探している
- ゲームやアニメには詳しくない。ITリテラシーは「スプレッドシートと画像アップロードができる」程度
- **現在の課題**: 既製のゲームは自分たちと無関係で、盛り上がりが一過性で終わる。
  かといって自作するスキルも時間もない
- **期待する解決策**: メンバーの顔写真を登録し、所属チームをそのままグループにして、
  **自分たちの組織だけのゲーム**を作れること。作ったものを全員に配って各自の端末で遊べること
- **懸念**: メンバーの顔写真を外部サービスにアップロードすることには抵抗がある。
  写真が端末の外に出ないことが導入の必須条件
- **典型的な使い方**: 事前に1時間かけてロスターを作り、ファイルを全員に配布。
  当日は各自の端末で遊ぶ

## 成功指標(KPI)

### 測定方法についての前提

本プロダクトは**サーバーを持たず、テレメトリを一切収集しない**（プライバシー配慮と、
静的ホスティングのみで完結させる設計方針による）。したがって DAU・継続率のような
ユーザー行動指標は原理的に測定できない。

そのため KPI は「**CI で自動測定できる品質指標**」と「**手動のユーザビリティテストで測定する指標**」の
2種類に限定して定義する。

### プライマリーKPI（自動測定・CI で毎回検証）

| 指標                     | 目標値                                | 測定方法                          | 期限   |
| ------------------------ | ------------------------------------- | --------------------------------- | ------ |
| 自動対局の完走率         | **100%**（シード0〜99の全局）         | `tests/engine/autoplay.test.ts`    | Step 3 |
| 不変条件の成立率         | **100%**（全局・全ステップ）          | 点数保存則・カード保存則・手札枚数 | Step 3 |
| 対局の決定性             | 同一シードで**完全に同一の結果**      | 同一シード2回実行の突き合わせ      | Step 3 |
| 検証ゲートの通過         | lint / typecheck / test / build / format すべて green | `npm run` 各コマンド | 全 Step |

### セカンダリーKPI

| 指標                         | 目標値                          | 測定方法                              | 期限   |
| ---------------------------- | ------------------------------- | ------------------------------------- | ------ |
| 自動対局100局の実行時間      | **1秒以内**                     | Vitest の実行時間                     | Step 3 |
| 本番バンドルサイズ           | **gzip 150KB 以内**             | `npm run build` の出力                | Step 4 |
| 1局あたりの所要時間（人間） | **3〜7分**                      | 手動計測（5局の平均）                 | Step 4 |
| 初回操作までの時間           | **30秒以内**にカードを1枚捨てられる | ユーザビリティテスト（ルールを知らない人3名） | Step 4 |
| ロスター作成の所要時間       | 12人分の登録が **30分以内**     | 手動計測（画像12枚 + グループ4つ）    | Step 6 |
| ロスター共有の成立           | 書き出したファイルを**別端末で読み込んで遊べる** | 手動テスト（書き出し→別ブラウザで読み込み→対局） | Step 6 |
| 実機統計との乖離の記録       | 乖離があれば**原因分析を文書化** | `.steering/*/design.md`               | Step 3 |

> **注**: 「実機統計との一致」を KPI にしていないのは、参照できる実測値（山切れ終了率 69.7% /
> 平均35打牌）が第三者の測定した1系統の統計であり、こちらの CPU の打ち方に強く依存するため。
> 一致させにいくと未確定のルール値に AI 由来の誤差を押し付けることになる。
> **一致ではなく、乖離の原因を説明できる状態**を成功と定義する。

## 機能要件

### コア機能(MVP)

#### 1. 対局エンジン（ルール再現）

**ユーザーストーリー**:
プレイヤーとして、原作と同じ手応えで遊ぶために、ポカジャンのルールが正確に再現された対局エンジンが欲しい

**受け入れ条件**:

- [x] 4人対戦で、反時計回りに「山から1枚引く → 1枚捨てる」を繰り返せる
- [x] 手札は常に7枚（自分の手番で引いてから捨てるまでの間だけ8枚）
- [x] 役は「同一メンバー3枚（3カード）」と「グループ全員1枚ずつ（3〜5人組）」の2系統が判定される
- [x] 役の構成カードが全て同色のとき、点数表どおりの同色ボーナスが加算される
- [x] ボーナスメンバーが役に含まれると1枚につき +90点が加算される
- [x] ツモ和了で他3人から等分、ロン和了で捨てた人が全額を支払う
- [x] **和了しても局が終わらず**、消費したカードが即時補充される
- [x] 補充で新たな役が成立したら連続して宣言できる
- [x] 他家の捨て札に対し、手番に関係なく割り込み宣言できる
- [x] 複数人が同時に宣言した場合、点数が高い方が優先され、同点なら捨てた人から近い方が優先される
- [x] 山札が尽きる、または誰かの点数が0以下になったら終局し、最終点数で順位が決まる
- [x] 山札は各メンバー9枚（3色×3枚）のプールから100枚を抽出して作られる

**優先度**: P0(必須) — **実装済み（Step 1〜3）**

#### 2. 対局ロジックの正しさの保証

**ユーザーストーリー**:
開発者として、UI の実装中にゲームロジックを疑わずに済むように、対局の正しさが自動テストで証明されていてほしい

**受け入れ条件**:

- [x] 4人の点数の合計が対局を通じて常に一定である（点数保存則）
- [x] 山札 + 全員の手札 + 全員の河 + 成立済みの役の合計枚数が常に一定で、カードの重複がない（カード保存則）
- [x] 終局していない限り、全プレイヤーの手札が規定枚数である
- [x] シードを変えた100局が例外なく終局する
- [x] 上記が100局の**全ステップ**で検証されている
- [x] エンジンが乱数を内部生成せず、同一シードから局を完全に再現できる
- [x] 宣言された役をエンジンが再計算して検証し、点数を偽装した入力が精算に影響しない

**優先度**: P0(必須) — **実装済み（Step 3）**

#### 3. CPU 対戦相手

**ユーザーストーリー**:
プレイヤーとして、1人でも対局を成立させるために、そこそこの判断をする CPU3人が欲しい

**受け入れ条件**:

- [x] 役が成立していれば必ず宣言する（攻略定石に準拠）
- [x] 複数の役が成立している場合、最も点数の高いものを選ぶ
- [x] どの役にも寄与しないカードを優先して捨てる
- [x] **他家の手札と山札の中身を参照しない**（公開情報のみで判断する）
- [x] 同じ局面に対して常に同じ判断を返す（乱数を使わない）
- [x] 難易度パラメータで挙動を切り替えられる

**優先度**: P0(必須) — **実装済み（Step 3）**

#### 4. 対局画面

**ユーザーストーリー**:
プレイヤーとして、実際に遊ぶために、手札をクリックして打てる対局画面が欲しい

**受け入れ条件**:

- [ ] 自分の手札が画面下に並び、自分の手番でクリックすると捨てられる
- [ ] 他3人の伏せ手札枚数・点数・直近の捨て札が見える
- [ ] 山札の残り枚数、ボーナスメンバー、今局の4グループが常に確認できる
- [ ] **あと1枚で役が完成するカードが黄色枠で強調される**（原作のリーチ表示に相当）
- [ ] 他家の捨て札で役が成立すると宣言ボタンと残り時間バーが表示される
- [ ] 制限時間が経過すると自動的にパスされる
- [ ] カードの移動（山→手札→河）と役成立がアニメーションで表現される
- [ ] 1局を最後まで人間の操作だけで完了できる
- [ ] スマートフォン幅（375px）でレイアウトが破綻しない

**優先度**: P0(必須) — Step 4

#### 5. カジノメタ（BET・精算・所持コイン）

**ユーザーストーリー**:
プレイヤーとして、1局ごとの結果に意味を持たせるために、コインを賭けて精算するループが欲しい

**受け入れ条件**:

- [ ] 対局前に BET 額（1000 / 2000コイン）を選択できる
- [ ] 所持コインが BET 額に満たない場合、その BET を選択できない
- [ ] 対局後に `(最終点数 × BET倍率 × 順位倍率) − BET額` で精算される
- [ ] 順位倍率が 1位2.5 / 2位1.5 / 3位1.0 / 4位1.0 で適用される
- [ ] 所持コインがブラウザを閉じても保持される
- [ ] 精算の内訳（最終点数・順位・倍率・増減）が結果画面で確認できる

**優先度**: P0(必須) — Step 5

#### 6. ロスターエディタ（自分たちの卓を作る）

本プロダクトの**中心的な価値**を担う機能。カードに描かれる内容をまるごとユーザーに開放する。

**ユーザーストーリー**:
チームのマネージャーとして、自分たちの組織だけのゲームを作るために、
メンバーの写真とチーム構成を登録できる設定画面が欲しい

**受け入れ条件（作成）**:

- [ ] メンバーとグループを追加・削除・改名できる
- [ ] メンバーに画像をアップロードでき、対局画面のカードに反映される
- [ ] メンバーをグループへ割り当て・付け替えできる
- [ ] アップロードした画像がブラウザを閉じても保持される
- [ ] **画像が未設定でも遊べる**（頭文字とアクセントカラーで描画される）
- [ ] 対局が成立しない構成（グループ数不足・人数が3〜5人の範囲外・総メンバー数不足）では保存できず、
      **何が足りないかが具体的に**表示される

**受け入れ条件（共有）**:

- [ ] ロスターを**画像を含む単一ファイル**として書き出せる
- [ ] 書き出したファイルを**別の端末・別のブラウザ**で読み込んで、そのまま対局できる
- [ ] 壊れた形式のファイルを読み込んでもクラッシュせず、エラー内容が表示される
- [ ] ファイルサイズが大きい場合に警告が表示される

**受け入れ条件（プライバシー）**:

- [ ] アップロードした画像が**外部に送信されない**（端末内のブラウザストレージのみ）
- [ ] 実在の人物の写真を扱う前提として、外部通信が発生しないことが利用者に明示される

**優先度**: P0(必須) — Step 6

#### 7. ルール設定

**ユーザーストーリー**:
プレイヤーとして、未確定の仕様が判明したときや好みのバランスにしたいときに、点数表などの数値を画面から変更したい

**受け入れ条件**:

- [ ] 点数表・初期点・BET設定などの数値を画面から編集できる
- [ ] 変更が次の対局から反映される
- [ ] 「デフォルトに戻す」で初期値へ復元できる
- [ ] 対局が成立しなくなる値（例: グループ人数が役判定の対応範囲外）は保存できず、理由が表示される

**優先度**: P1(重要) — Step 6

### 将来的な機能(Post-MVP)

#### オンライン4人対戦

人間同士の対戦。サーバーとアカウント管理が必要になるため、
「サーバーを持たない」という現在の設計方針を根本から変更することになる。

**優先度**: P2(できれば)

#### 「ダマポカジャン」の CPU 実装

安手を見送って同色の高得点を狙う戦術。現在の CPU は「役が揃えば即宣言」で固定されている。
実機の平均打牌数（35）に本実装（21.7）が届いていない原因はここにあると分析済み。

**優先度**: P2(できれば)

#### 対局のリプレイ・中断復帰

エンジンが「シード + アクション列」だけで局を完全に再現できる設計になっているため、
土台は既にある。UI と保存形式の設計が必要。

**優先度**: P2(できれば)

#### 対局ログの可視化

「どの局面でどの役を狙うべきだったか」を振り返る学習支援。

**優先度**: P2(できれば)

#### サウンド・BGM

カードを引く / 捨てる / 役が成立する際の効果音と、対局中の BGM。
体験の質は上がるが、遊べること自体には影響しない。
音源を同梱する場合はライセンスの確認が別途必要になる。

**優先度**: P2(できれば)

#### ロスターの共有をより簡単にする手段

現状はファイルの受け渡しを想定している。QR コードや URL による共有は、
画像を含むデータ量の問題とサーバーを持たない方針との兼ね合いで別途検討が必要。

**優先度**: P2(できれば)

## 非機能要件

### パフォーマンス

- 自動対局100局の実行時間: **1秒以内**（回帰テストとして日常的に回せる速度を保つ）
- 対局画面の操作応答: カードクリックから描画反映まで **100ms 以内**
- 本番バンドルサイズ: **gzip 150KB 以内**
- 初期表示（Time to Interactive）: 一般的な回線で **2秒以内**
- 役判定・待ち計算: 1手番あたり **10ms 以内**（体感の遅延を生まない）

### ユーザビリティ

- ルールを知らない人が **30秒以内**に最初のカードを捨てられる（ユーザビリティテスト、3名中3名）
- ロスター作成が**IT の専門知識なしで完了できる**（画像アップロードとテキスト入力のみで、
  ファイル形式やサイズの事前調整を利用者に要求しない）
- 画面上に**常に**「今局の登場グループ」「ボーナスメンバー」「山札残り」が表示されている
- あと1枚で成立する役が視覚的に判別できる（黄色枠）
- スマートフォン幅 **375px** でレイアウトが破綻しない
- 日本語表示（多言語対応は行わない）

### 信頼性

- **点数保存則**: 4人の点数の合計が対局を通じて変化しない（100局×全ステップで検証）
- **カード保存則**: 場に存在するカードの総数と一意性が保たれる（同上）
- **決定性**: 同一シードから完全に同じ対局が再現される
- 不正なアクション・偽装された役の宣言が**黙って無視されず**、必ず例外として表面化する
- 所持コインとロスターの永続化データが、通常の操作で失われない
- 壊れた形式のロスターを読み込んでもクラッシュせず、エラーとして扱われる

### セキュリティ・プライバシー

**実在の人物の顔写真が登録される前提**で設計する。組織での利用を想定した場合、
これが導入可否を決める最重要要件になる。

- ユーザーがアップロードした画像を**外部へ送信しない**（端末内のブラウザストレージのみ）
- 外部サービスへの通信を行わない（静的ファイルの配信のみで動作する）。
  画像を扱う処理はすべてブラウザ内で完結させる
- テレメトリ・アナリティクスを**一切収集しない**
- 登録した内容を**利用者が削除できる**（メンバー削除時に画像データも破棄される）
- 書き出したロスターファイルには個人情報（顔写真・氏名）が含まれるため、
  **取り扱いに注意が必要である旨を書き出し時に明示する**
- **公式の著作物（イラスト・ロゴ・キャラクター名）をリポジトリに一切含めない**

### スケーラビリティ

- ルールの数値がすべて設定として外部化され、コード変更なしに調整できる
- ロスターのメンバー数・グループ数を増減できる（対局成立の下限は検証で担保）。
  **20〜30人規模の組織を登録しても、作成操作と対局の動作が破綻しない**
- 画像の保存先が localStorage の容量制限に縛られない（20人分の顔写真を登録できる）
- 役の種類を追加する場合、点数表への追加と判定ロジック1つの追加で済む構造を保つ
- カードの色数を変更しても役判定のコードを変更せずに済む

### 保守性

- ルールエンジンが UI フレームワークに依存しない（静的解析で機械的に担保）
- エンジンが乱数と時刻を内部生成しない（テストの決定性を保つ）
- 各実装ステップで要求・設計・タスクの記録を残す

## スコープ外

明示的にスコープ外とする項目:

- **オンライン対戦・マルチプレイヤー通信**（サーバーを持たない方針のため）
- **アカウント登録・ログイン・クラウド同期**
- **テレメトリ・アナリティクス・行動ログの収集**
- **多言語対応**（日本語固定）
- **対局中のセーブ・中断復帰**（リロードで対局は破棄される）
- **公式キャラクター素材の同梱・配布**
- **課金・実際の金銭を伴う要素**（コインはゲーム内の数値のみ）
- **原作の他のミニゲーム**

> **サウンド・BGM** は当初スコープ外としていたが、「将来的な機能」の P2 へ移動した。
> MVP には含めないが、恒久的に作らないという判断ではない。
